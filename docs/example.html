One mapping, end to end

We follow one small path through the XML: raw orders in, STG_ORDERS out. It is short, but it touches every piece: a PC Source, three kinds of box, a PC Target, and the session and workflow that run it.

The path lives inside mapping m_FL_JS_STAGING_FULL L90, which writes 6 PC Targets. Here we look at the orders path only. All XML on this page was pulled from the file by a script, and all SQL is the converter's own output. Attributes are trimmed to the ones that matter, and line numbers open GitHub.

1 · Who runs it: workflow and session

The workflow runs tasks in order. Each session runs one mapping. Our path sits in the first session.

What the session adds

Truncate target first?
The session option says NO L919, but the target's Pre SQL empties it anyway: TRUNCATE TABLE STG.STG_ORDERS L541. So every run is a full reload.
Treat source rows as
Insert L995

None of this changes what is computed. It is about how rows are written. dbt handles that with materialization: each model is a table, rebuilt on every run (decision Q9).

What we do: the SQL copies the connectors exactly, so subtotal_cents really holds dollars, and every one of these columns gets a flag. This is decision D1: we copy the XML, we don't fix it.
